## 第2課題(やり直し) — ページに"動き"をつける

**内容**: ボタンを押すと反応するページを1つ作る。

**状態**: 完了(2026-09-10)。

**やりたかったこと**: 「いろいろ試験的に試してみたい」というご希望から、トップページの判子(ロゴ)を押すと、判子が浮き上がってお店の紹介ページへ移動する、という動きに挑戦した。

**試行錯誤の経緯**:
1. 最初はクリックで判子が上に移動+少し拡大(1.15倍)して、0.65秒後にページ遷移する形で実装
2. 実機で試したところ「ハンコ押せませんよ」と反応が無く、原因を切り分け: ファイルを`file:///...`として直接ダブルクリックで開いていたため、一部のブラウザ環境でJavaScriptによるページ遷移(`window.location`)が制限されていたと判明。ローカルサーバー(`http://localhost:8768`)経由で開くことで解決
3. 動き自体は起きたが、「思い描いていたのは、判子が横や上に動くのではなく、その場でだんだん大きくなりながら手前に浮かび上がってくるイメージ」というフィードバックを受け、演出を作り直した: 判子がその場で6倍に拡大しながら光り、同時に周りの文字がふわっと消えていく形に変更
4. 「大きくなる速度をもっと遅く(半分程度)、かつ判子自体もゆっくり透明になって消えていく」という追加フィードバックを受け、拡大・消滅にかける時間を1.4秒→2.8秒に延長し、判子自身にもopacityのフェードアウトを追加

**学び**: 「動きをつける」という課題は、コードが動くかどうかだけでなく、①ローカルファイルの開き方(`file://`と`http://`の違い)が動作に影響すること、②言葉で説明された動きのイメージを、実際に動くものとして何度か調整しながら近づけていく必要があること、の両方を体験できた回になった。

**成果物**: [index.html](../index.html)(判子のクリックアニメーション)、[shops/jizoyokan.html](../shops/jizoyokan.html)(仮の遷移先ページ)

## 第11課題(やり直し) — 第3週の関門③：GitHubデビュー

**内容**: GitHubアカウントを作り、リポジトリを作成してプロジェクトをpushする。

**状態**: 完了(2026-09-10)。

**経緯**:
1. 最初、岩瀬様から「新しいGitHubアカウントを作りましょう」との提案があったが、アカウント作成(パスワード入力等)はClaude側では代行できない操作のため、ご本人にお願いする形で`github.com/signup`を開いたところ、自動化ツールからのアクセスがGitHub側にブロックされ(403)、サインアップ画面が表示できなかった
2. 岩瀬様が実際のブラウザで`github.com/signup`を試みた際、既存の`iwasegiken`アカウントでログイン済みの状態だったため、代わりに既存リポジトリ`iwasegiken/kyuseki-meguri-note`が使えないか、名前を変更できないか、と提案があった
3. しかし`kyuseki-meguri-note`は既に「旧跡めぐりノート」という別プロジェクトの実物のリポジトリ(実際のコミット履歴・複数ファイルあり)と確認し、転用すると混乱するため見送りを提案。代わりに、新しいアカウントを作らずとも、既存の`iwasegiken`アカウントに**新しいリポジトリ**を1つ追加すれば十分、という方針に落ち着いた
4. `gh auth switch --user iwasegiken`でアカウントを切り替え、`gh repo create iwasegiken/hyakunen-sanpo --private`で非公開リポジトリを新規作成し、`git push -u origin main`でpush。作業後、既定の`claude-code-club`アカウントへ戻した

**学び**: GitHubアカウントの数にもリポジトリの数にも上限は無いこと、1つのアカウントに複数の無関係なプロジェクトを共存させられること、既存の実物リポジトリを安易に転用すると別プロジェクトと混同する危険があること、を実地で確認できた回になった。

**成果物**: https://github.com/iwasegiken/hyakunen-sanpo (非公開)

### つまずき: 「入力した文字が消える」— 不具合ではなく仕様だった

**岩瀬様からの報告**: 「入力しても文字が消えてしまう」。

**Claudeの誤診(3回)**: Claudeはこれを日本語入力(IME)の不具合と決めつけ、3回作り直した。

| 案 | 作り | 結果 |
|---|---|---|
| 1 | `st.form`(既定) | 消えると報告 |
| 2 | フォームをやめて`st.text_input`+ボタン+`st.rerun()` | 消えると報告 |
| 3 | 1行欄を`st.text_area`に置換 | 消えると報告 |
| 4 | `st.form(..., enter_to_submit=False)` | 消えると報告 |

途中、保存ファイル`data/shops.json`に「創業１１０」(「年」が欠けた記録)があったのを見て、Claudeは「**変換確定のEnterで文字が捨てられている証拠だ**」と判断した。しかしこれは**単に岩瀬様が「年」まで入力せずに保存しただけ**の可能性が高く、決めつけだった。

**対処**: `st.empty()`でメッセージの置き場所をフォームより**先に**確保し、保存結果を画面上部に出すようにした。文言も「(全 N 件)。次のお店を入力できるように入力欄は空にしました。入力した内容は data/shops.json に残っています」と、何が起きたか分かるように変えた。

**学び(ここが一番大事)**:
- **症状の報告を受けたら、まず「いつ・どこで」を本人に確認する。** Claudeは確認せずに原因を推測し、3回とも外した。最初に「どの瞬間に消えますか」と聞いていれば1回で終わっていた

- 副産物として`enter_to_submit=False`は残した。既定のままだと日本語の変換確定Enterで意図せず送信されてしまうため、日本語で使うフォームでは実際に有用

### 作り直し: 「確認してから保存」へ

上の対処(保存してから、その内容を画面上部に出す)に対して、岩瀬様から2つの指摘を受けた。

1. **「記録したなら、それが正しいかどうか確認してからでないとだめ」** — 保存してから確認するのでは順序が逆。確認は保存の**前**にあるべき
2. **「上に書く仕様はいやです。スマートではない。入力画面からかっこよくしてください」** — 確認内容が画面上部に長く表示されるのは野暮ったい

これを受けて作り直した:

- ボタンを「**確認する**」1つにし、押すと**小窓(`st.dialog`)**が開いて入力内容が項目名つきで並ぶ。そこで「書き直す」か「記録する」を選ぶ。**確認の時点では保存していない**
- 保存できたことは、小さな通知(`st.toast`)と一行の報告だけで伝える。画面を占領しない
- 見た目をサイト本体と同じ意匠に統一(判子ロゴ、藍色の背景、金色の項目名、朱色のボタン、明朝体の題字、下線だけの入力欄)。`style.py`と`.streamlit/config.toml`に分離した

**動作確認(Claudeが別ポート8502で実施、岩瀬様の画面には触れずに検証)**:

| 確かめたこと | 結果 |
|---|---|
| 「確認する」で小窓が開き、内容が正しく並ぶ | 名前・種類・創業年とも一致、空欄は「—」表示 |
| 確認だけでは保存されない | 件数 11 → 11(変わらず) |
| 小窓の「記録する」で保存される | 件数 11 → 12 |
| 保存内容がファイルの中身と一致 | `創業１３０年` / `20:22:49` 一致 |
| 保存後も入力が残る | 消えない |

**学び**:
- **確認は、取り返しがつかなくなる前に置く。** 「保存してから見せる」は、間違っていても直せない。順序が逆だと指摘されて初めて気づいた
- **報告する前に、自分で動かして確かめる。** 岩瀬様の「記録したなら正しいかどうか確認してからでないとだめですよ」は、ツールの作りだけでなくClaudeの報告の仕方への指摘でもあった。以降は別ポートで起動して検証してから報告する形に変えた
- **見た目も仕様のうち。** 道具の既定の見た目のままだと、せっかくサイト本体で作った世界観が途切れる。運営ツールでも同じ意匠に揃えた
- Streamlitの見た目の設定(`style.py`・`config.toml`)は、**ブラウザのF5では反映されない。サーバーの再起動が必要**

**残ったもの**: 動作確認で12件のテスト記録が入っている(`【動作確認用】`で始まるものはClaudeの検証用)。第15課題の一覧・削除機能の練習台にする。

**内容**: ログイン機能を追加し、ログインした本人のデータだけが見えるようにする。パスワード等の機密情報は保存しない方針を確認し、空欄・異常入力で落ちないようにする。

### 進め方の反省(Claude)

最初、岩瀬様が「複数人が使える形(A案)」を選ばれた直後に、Claudeが実装からテストまで一人で全部やってしまった。登録する・間違った合言葉を試す・他人に見えないことを確かめる——**それが第16課題そのもの**なのに、岩瀬様の手が入る前に終わらせてしまった。

### 決めたこと: 合言葉をどう保存するか

3案を並べて岩瀬様に選んでいただいた。

| 案 | 内容 | 判断 |
|---|---|---|
| ① そのまま保存 | `"岩瀬": "sakura2026"` | — |
| ② 鍵をかけて保存(戻せる) | 鍵があれば元に戻る | 岩瀬様が当初選択 |

岩瀬様は当初②を選ばれたが、Claudeから次の3点をお伝えしたうえで③に変更となった。

### 手を動かして確かめたこと(岩瀬様が操作)

**1. 「戻せない変換」を自分の目で見る**

```
sakura → d41dc6385e804fd6c6fe049ecd56a3c1bafa61e669d4f3b49082ff56f8ade10d
sakura → d41dc6385e804fd6c6fe049ecd56a3c1bafa61e669d4f3b49082ff56f8ade10d  ← 毎回同じ
sakurb → e59822dbda3d31180c744d6a712220e283dbc29f1db22d0b1f5081e4a02f3cbe  ← 1文字違うと別物
```

「毎回同じ」だから保存した値と比べて判定できる。「1文字違うと別物」だから似た合言葉から推測できない。

**2. 弱点を自分で考える**

Claudeが「この仕組みの弱点はどこか」と尋ねたところ、岩瀬様の答えは「**自分しか知らない情報にする**」。**半分正解**だった。

- 意外な点: **塩は秘密でなくてよい**。ファイルに丸見えで保存する。役割は「秘密を守る」ことではなく「**使い回しを禁じる**」こと。世界共通の対応表が使えなくなり、同じ合言葉の人が同じ値にならない

**3. 塩の効果を確かめる**

```
aaa111 + sakura → 4115ff0b25b5...
bbb222 + sakura → 4d6a009e93c8...   ← 同じ sakura なのに別物
```
どちらも塩なしの `d41dc638...` とも違う ＝ 事前に作られた対応表が無効になっている。

**4. `auth.py` を単体で試す**(画面を作る前に、コマンドで直接)

| 試したこと | 結果 |
|---|---|
| 登録 → `data/users.json` を開く | `salt` と `hash` だけ。**`sakura` という文字はどこにもない** |
| 正しい合言葉 | `True` |
| 違う合言葉 / 空欄 / いない人 | 全部 `False`(**落ちない**) |
| 同じ名前で再登録 | 「すでに使われています」 |
| 名前が空 / 合言葉2文字 | それぞれ理由を返す(**落ちない**) |

# コース4「独り立ち編」（第43〜57課題）

## 第43課題 — 速い・遅いを見抜く（アルゴリズムと計算量）

**内容**: ①一覧や検索の処理を見て、データが1万件・10万件に増えたとき遅くなりそうな所を指摘する ②速いやり方に書き直す ③「計算量(O記法)」を自分のアプリの例で説明する。

**状態**: 完了(2026-09-26)。

### ① 診断 — 実際のコードを数えた

推測せず、`grep`で呼び出し箇所を数えてから診断した。遅くなる場所は4つ。

| | 場所 | 中身 |
|---|---|---|
| **問題1** | 一覧の描画ループ | **全件をそのまま画面に出す。1件につき画面部品6個** |
| 問題2 | `add_shop` / `update_shop` / `delete_shop` | 1件足すのに**全件読んで全件書き戻す** |
| 問題3 | `find_shop` | 1件探すのに**端から順に**見る |
| 問題4 | `load_shops()` が4か所 | 1回の画面表示で同じファイルを何度も読む |

**問題1が本丸**だった。

| 件数 | 作られる画面部品 |
|---|---|
| 1件 | 6個 |
| 1万件 | 6万個 → 何十秒 |
| 10万件 | **60万個 → ブラウザが固まる** |

> **人間は1万件を一度に見られないのに、全部作っていた。**

岩瀬様の判断で問題1から着手（問題3は第44課題「データ構造」の題材そのもの）。

### ② ページ送りに直した

1ページ20件に区切り、`PER_PAGE = 20` と前後のボタンを追加。

| 件数 | 直す前 | 直した後 |
|---|---|---|
| 51件 | 306個 | **120個** |
| 1万件 | 6万個 | **120個** |
| 10万件 | 60万個 | **120個** |

**件数に比例する O(n) → 件数に関係なく一定 O(1)** になった。

### バックアップがあったから実験できた

記録が1件では効果が見えないので、**テスト記録を50件追加して体感**し、そのあと**バックアップから戻した**。


**第41課題でバックアップと復旧を用意したから、安心して壊す実験ができた。** 昨日まではできなかったこと。

### ③ 計算量(O記法)を自分の言葉で

**「速い・遅い」ではなく「件数が増えたとき、手間がどう増えるか」の言い方。**

| 書き方 | 意味 | 百年散歩の例 |
|---|---|---|
| **O(1)** | 件数が増えても手間は変わらない | ページ送りの1ページ＝いつも20件 |
| **O(n)** | 件数に比例して増える | 一覧を全件出す(直す前)／`find_shop`が端から探す |

> **O(n)** ＝ 電話帳を1ページ目から順にめくって探す。1万人載っていれば最悪1万ページ
> **O(1)** ＝ 「さ行の3ページ目」と分かっていてそこだけ開く。何人載っていても1回

**学び（ここが肝）**:
- **10件のときは、どちらも一瞬。差が見えない。** 1万件になって初めて地獄になる
- **だから「見抜く」。** 遅くなってから気づくのでは遅い。作るときに「件数が増えたらどうなる？」と考える
- 百年散歩はいま1件。**増える前に手を打てた**
